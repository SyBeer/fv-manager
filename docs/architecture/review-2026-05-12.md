## 🏢 Enterprise Architect

## Scenariusze biznesowe

**Główny użytkownik (prosument):** Właściciel instalacji fotowoltaicznej, który chce świadomie zarządzać zwrotem z inwestycji. System realizuje trzy cele biznesowe:

1. **Kontrola ROI** — śledzenie, kiedy inwestycja (panele, inwerter, magazyn, ładowarka EV) się zwróci. Ekstrapolacja liniowa na bazie historycznych oszczędności daje prosumentowi konkretną datę break-even. Wartość: decyzje o kolejnych etapach inwestycji (np. dokupienie magazynu) oparte na danych, nie intuicji.

2. **Optymalizacja zużycia energii** — rozbicie na autokonsumpcję, net-metering pool (80%), pobór z sieci. Prosument widzi, ile realnie oszczędza vs ile "przepada" w rozliczeniu. Wartość: motywacja do przesunięcia zużycia w godziny produkcji.

3. **Konwergencja FV + EV** — obliczanie oszczędności z ładowania pojazdów elektrycznych vs paliwo. Obsługa wielu pojazdów z osobną efektywnością. Wartość: pełny obraz TCO ekosystemu energetycznego gospodarstwa domowego.

**Interesariusze drugorzędni:**
- **Ekosystem Home Assistant** — aplikacja jako add-on w sidebarze HA, co umieszcza ją w centrum smart-home. Integracja z HA Statistics API i Tesla Fleet API poszerza bazę użytkowników o społeczność HA (~500k+ aktywnych instalacji).

## Ocena strategiczna

### Alignment z celami

| Cel strategiczny | Realizacja | Ocena |
|---|---|---|
| Samowystarczalność energetyczna | Pełne śledzenie przepływów energii, net-metering | **Silna** |
| Świadome decyzje inwestycyjne | ROI, sensitivity analysis, break-even | **Silna** |
| Integracja z ekosystemem smart-home | HA add-on, ingress, Tesla API | **Umiarkowana** — działa, ale jednokierunkowa (tylko odczyt) |
| Skalowalność na wielu użytkowników | Brak — SQLite, single-tenant, brak auth | **Słaba** |

### Ryzyka strategiczne

1. **Uzależnienie od modelu net-meteringu 80%** — hardcoded `sent_to_grid * 0.8` w `calculations.py`. Zmiana regulacji (np. net-billing, który już obowiązuje w PL od 2022 dla nowych prosumentów) uczyni kalkulacje błędnymi. To nie jest parametr konfiguracyjny — wymaga zmiany kodu.

2. **Monolityczna architektura w `main.py`** — pojedynczy plik zawiera endpointy HTTP, logikę biznesową (helpery), integracje z HA/Tesla, obsługę CSV. Brak separacji warstw (controller / service / repository). Każda zmiana w integracji ryzykuje regresję w kalkulacjach.

3. **SQLite jako jedyny storage** — poprawny wybór dla single-tenant embedded, ale brak backupu, brak migracji wersjonowanych (ALTER TABLE "na żywo" przy starcie), brak WAL mode explicite. Utrata `fv.db` = utrata wszystkich danych historycznych.

4. **Brak walidacji danych wejściowych na granicy systemu** — formularze HTML nie mają walidacji server-side widocznej w kontekście. Odczyty mogą zawierać `sent_to_grid > production` (importer.py to sprawdza, ale formularz ręczny prawdopodobnie nie).

5. **Zależność od CDN dla UI** — Flatpickr i potencjalnie Chart.js ładowane z `cdn.jsdelivr.net`. W kontekście HA add-on (lokalna sieć, potencjalnie bez internetu) to punkt awarii.

### Zależności architektoniczne

```
[Prosument] → [FV Manager (FastAPI)]
                  ├── SQLite (local/embedded)
                  ├── Home Assistant API (opcjonalnie)
                  │     └── Statistics API (solar production)
                  ├── Tesla Fleet API (opcjonalnie)
                  └── CDN (jsdelivr — Flatpickr, Chart.js)
```

Brak message brokera, brak cache, brak kolejki — adekwatne dla skali, ale oznacza brak możliwości asynchronicznego pobierania danych z HA/Tesla (np. scheduled sync).

## Luki i rekomendacje EA

### 1. **Brak capability: model rozliczeniowy jako konfiguracja**
- **Luka:** Net-metering 80% jest jedynym modelem. Prosumenci od 2022 rozliczani w net-billingu (sprzedaż po cenie rynkowej, zakup po taryfie).
- **Rekomendacja:** Wyodrębnić strategię rozliczeniową (`SettlementStrategy`) jako parametr w `ev_settings` lub osobną tabelę. Minimum: `settlement_model ENUM('net_metering_80', 'net_billing')` + odpowiednia logika w `calc_monthly`.
- **Priorytet:** Krytyczny — bez tego aplikacja jest użyteczna tylko dla prosumentów sprzed lipca 2022.

### 2. **Brak capability: backup i odtwarzanie danych**
- **Luka:** Brak eksportu/importu pełnego stanu (inwestycje + odczyty + pojazdy + ustawienia). CSV eksportuje tylko odczyty.
- **Rekomendacja:** Endpoint `/backup` generujący SQLite dump lub JSON z pełnym stanem. W HA add-on: integracja z HA snapshot/backup system.
- **Priorytet:** Wysoki — dane historyczne są niewznawialne.

### 3. **Brak separacji warstw (Architecture Building Block)**
- **Luka:** `main.py` łączy routing, logikę biznesową i integracje. Brak repozytorium (warstwa dostępu do danych tightly coupled z endpointami).
- **Rekomendacja:** Refaktor wg wzorca:
  - `src/routers/` — endpointy FastAPI (thin controllers)
  - `src/services/` — logika biznesowa (już częściowo istnieje)
  - `src/repositories/` — dostęp do SQLite
  - `src/integrations/` — HA, Tesla
- **Priorytet:** Średni — nie blokuje użytkownika, ale blokuje rozwój.

### 4. **Brak capability: automatyczny import danych**
- **Luka:** Pobieranie danych z HA wymaga ręcznego kliknięcia. Brak scheduled sync (np. pierwszy dzień miesiąca — pobierz produkcję za poprzedni miesiąc).
- **Rekomendacja:** CRON-like task w HA add-on (np. `apscheduler`) lub webhook z HA automation.
- **Priorytet:** Średni — znacząco poprawia UX i kompletność danych.

### 5. **Brak capability: multi-tenancy i uwierzytelnianie**
- **Luka:** Brak auth. W HA add-on chroniony przez ingress, ale standalone — otwarty na porcie 8010.
- **Rekomendacja:** Dla standalone: minimum basic auth lub HA-style API token. Dla przyszłej skalowalności: rozważyć SaaS model z PostgreSQL.
- **Priorytet:** Niski (jeśli tylko HA add-on) / Wysoki (jeśli planowany standalone deployment).

### 6. **Brak wersjonowanej migracji schematu**
- **Luka:** Migracje przez `ALTER TABLE ... ADD COLUMN` z `try/except` przy starcie. Brak śledzenia, która migracja została zastosowana.
- **Rekomendacja:** Prosta tabela `schema_version` + sekwencyjne migracje. Nie potrzeba Alembic — wystarczy lista SQL w kodzie z numerem wersji.
- **Priorytet:** Średni — rośnie z każdą nową kolumną.

### Podsumowanie TOGAF — Capability Heat Map

| Capability | Dojrzałość | Kierunek |
|---|---|---|
| Śledzenie przepływów energii | 🟢 Dojrzała | Utrzymanie |
| Kalkulacja ROI | 🟡 Częściowa | Dodać net-billing |
| Integracja EV | 🟢 Dojrzała | Utrzymanie |
| Integracja HA/Tesla | 🟡 Częściowa | Automatyczny sync |
| Backup / DR | 🔴 Brak | Priorytetowe |
| Modularność kodu | 🟡 Częściowa | Refaktor warstw |
| Bezpieczeństwo | 🟡 Częściowa | Auth dla standalone |
| Migracje schematu | 🔴 Ad-hoc | Schema versioning |

---

**Konkluzja:** FV Manager dobrze realizuje core value proposition dla prosumenta na starym net-meteringu. Największe ryzyko strategiczne to hardcoded model rozliczeniowy — ogranicza bazę użytkowników do kurczącego się segmentu. Największe ryzyko operacyjne to brak backupu. Architektura monolityczna jest akceptowalna na obecną skalę, ale powinna ewoluować w kierunku separacji warstw przed dodaniem kolejnych integracji.

### Styl architektoniczny
**Monolityczna aplikacja webowa SSR** — FastAPI + Jinja2 + SQLite. Cała logika (routing, biznes, persistence, integracje zewnętrzne) skupiona w jednym procesie. Dla skali tego projektu (single-user, single-instance) to uzasadniony wybór.

### Mocne strony

| Aspekt | Ocena |
|--------|-------|
| **Prostota deploymentu** | SQLite + single process = zero DevOps overhead. Idealny dla HA Add-on |
| **Separation: calculations.py** | Logika obliczeniowa wyizolowana, testowalną — dobry wzorzec |
| **Ingress support** | `root_path` / `INGRESS_PATH` poprawnie obsługiwany w redirectach i linkach |
| **Idempotentne migracje** | `ALTER TABLE` z `try/except` — pragmatyczne dla SQLite bez Alembic |
| **CSV round-trip** | Eksport → import bez modyfikacji — dobry UX backup |

### Problemy strukturalne

| Problem | Wpływ | Priorytet |
|---------|-------|-----------|
| **God Object: `main.py`** | Routing, walidacja, integracje HA/Tesla, helpery Jinja — wszystko w jednym pliku. Utrudnia nawigację i testowanie | Wysoki |
| **Brak warstwy repository** | Raw SQL rozrzucony po `main.py` — brak abstrakcji nad `db.py`. Zmiana schematu wymaga grepowania całego codebase | Wysoki |
| **Inline CSS w templates** | Powtórzony `style="color:#22c55e;"` w dziesiątkach miejsc. Zmiana palety kolorów = ręczna edycja każdego template | Średni |
| **Brak walidacji wejścia** | Formularze POST trafiają do raw SQL bez walidacji (poza HTML `required`). Brak Pydantic models | Wysoki |
| **Hardcoded business rules** | `0.8` net-metering factor, domyślne ceny — zakopane w kodzie bez konfiguracji | Średni |
| **Brak auth** | Każdy z dostępem do portu ma pełny CRUD. OK dla HA ingress, ryzykowne w standalone | Niski* |

*\*Niski bo HA ingress zapewnia auth, a standalone to zazwyczaj localhost.*

## 2. Architecture Decision Records

### ADR-001: SQLite jako jedyny backend bazy danych

- **Kontekst**: Aplikacja działa jako single-user HA Add-on lub standalone. Dane to kilkaset rekordów (odczyty miesięczne, inwestycje). Brak potrzeby concurrent writes ani replikacji.
- **Decyzja**: SQLite z aiosqlite — plik w `/data/fv.db` (HA) lub `data/fv.db` (standalone).
- **Konsekwencje**:
  - (+) Zero konfiguracji, zero dependencji infrastrukturalnych
  - (+) Backup = kopia jednego pliku
  - (+) Idealny do HA Add-on (filesystem persistence)
  - (−) Brak concurrent writes (WAL mode łagodzi, ale nie eliminuje)
  - (−) Brak natywnych migracji — ręczne `ALTER TABLE`
  - (−) Brak connection pooling — każdy request otwiera nowe połączenie

### ADR-002: Server-Side Rendering zamiast SPA

- **Kontekst**: Aplikacja dashboardowa z formularzami CRUD. Docelowo embeddowana w HA panel (iframe/ingress). Brak potrzeby rich interactivity ani offline mode.
- **Decyzja**: Jinja2 templates + Tailwind CSS + Chart.js dla wykresów. Brak frameworka JS.
- **Konsekwencje**:
  - (+) Zero build pipeline, natychmiastowy reload
  - (+) Pełna kompatybilność z HA ingress (root_path w linkach)
  - (+) Mniejszy bundle, szybszy TTI
  - (−) Każda interakcja = full page reload (np. zapis odczytu → redirect)
  - (−) Inline styles zamiast komponentów — brak reuse
  - (−) Chart.js wymaga `<script>` bloków w template — mieszanie logiki prezentacji z danymi

### ADR-003: Monolityczny `main.py` jako punkt wejścia

- **Kontekst**: Projekt rozrastał się organicznie — od prostego CRUD do integracji z HA, Tesla, multi-vehicle EV, sensitivity analysis.
- **Decyzja**: (Domyślna, nie świadoma) — cały routing i logika integracji w jednym pliku.
- **Konsekwencje**:
  - (−) `main.py` prawdopodobnie >800 linii — przekracza próg łatwej nawigacji
  - (−) Testowanie endpointów wymaga mockowania całego app context
  - (−) Dodanie nowej integracji (np. Shelly, SolarEdge API) dalej rozbudowuje ten plik
  - **Rekomendacja**: Refaktor do `routers/` (FastAPI `APIRouter`) — osobne moduły: `readings.py`, `investments.py`, `ev.py`, `integrations.py`, `import_export.py`

### ADR-004: Net-metering 0.8 jako stała biznesowa

- **Kontekst**: Model oszczędności oparty na starym polskim net-meteringu (80% oddanej energii wraca). Ten model został zastąpiony net-billingiem (od 2022) dla nowych instalacji.
- **Decyzja**: Współczynnik `0.8` hardcoded w `calculations.py`.
- **Konsekwencje**:
  - (+) Prosty model, łatwy do zrozumienia
  - (−) Brak wsparcia dla net-billingu (nowe instalacje rozliczane wg ceny rynkowej)
  - (−) Zmiana współczynnika wymaga edycji kodu, nie konfiguracji
  - **Rekomendacja**: Wyciągnąć do `ev_settings` lub nowej tabeli `billing_model` z wyborem: `net_metering_080` | `net_billing` | `custom`

## 3. Wymagania niefunkcjonalne (NFR)

| Kategoria | Wymaganie | Metryka | Status |
|-----------|-----------|---------|--------|
| **Wydajność** | Dashboard ładuje się poniżej progu percepcji | p95 < 300ms (SSR + SQLite) | OK — SQLite na kilkuset rekordach jest instant |
| **Wydajność** | Kalkulacja ROI z sensitivity table | p95 < 500ms dla 60 odczytów × 5 wariantów cen | OK — pure Python, brak I/O w pętli |
| **Niezawodność** | Brak utraty danych przy restarcie kontenera HA | RPO = 0 (SQLite WAL + persisted volume) | OK — `/data/` mapowane na persistent storage |
| **Niezawodność** | Odporność na brak połączenia z HA/Tesla | Graceful degradation — ręczny import dalej działa | Częściowe — brak obsługi timeout/retry w integracji |
| **Bezpieczeństwo** | Brak SQL injection | 100% parameterized queries | Do weryfikacji — raw SQL w `main.py` wymaga audytu |
| **Bezpieczeństwo** | Token HA nie wycieknie do frontendu | Token tylko w env/DB, nigdy w HTML | Do weryfikacji |
| **Utrzymywalność** | Nowa rola danych (np. magazyn energii) < 1 dzień pracy | Dodanie tabeli + CRUD + template ≤ 8h | Zagrożone — `main.py` monolit spowalnia onboarding |
| **Testowalność** | Pokrycie logiki biznesowej testami | ≥ 80% branch coverage `calculations.py` | Częściowe — 5 testów, brak edge cases (ujemne wartości, NaN) |
| **Przenośność** | Działa na aarch64, amd64, armv7, armhf | Build na 4 architekturach | OK — `build.yaml` poprawny |
| **Observability** | Logi błędów integracji HA/Tesla | Structured logging z timestampem | Brak — brak loggera, prawdopodobnie bare `print()` |

## 4. Rekomendacje refaktoryzacyjne (priorytetyzowane)

- ReadingCreate, ReadingUpdate

### P3 — Rozbicie `main.py` na routery
```
src/

    readings.py
    investments.py

# Zamiast hardcoded 0.8:
class BillingModel(Enum):

```

### P5 — Structured logging
```
Zastąpić print() → logging.getLogger(__name__)

Logi: integracje HA/Tesla, import CSV, błędy walidacji
```

## 5. Ocena ryzyk

| Ryzyko | Prawdopodobieństwo | Wpływ | Mitygacja |
|--------|-------------------|-------|-----------|
| SQL injection przez brak parametryzacji | Średnie | Krytyczny | Audyt `main.py`, Pydantic models |

## Podsumowanie

FV Manager to **dobrze dopasowany do swojej skali** projekt — SQLite + SSR + HA Add-on to trafny stack dla single-user dashboardu energetycznego. Główne ryzyko architektoniczne nie leży w wyborze technologii, lecz w **braku wewnętrznej struktury**: monolityczny `main.py`, rozproszony SQL, brak walidacji wejścia. Priorytet #1 to bezpieczeństwo (walidacja + audyt SQL), priorytet #2 to utrzymywalność (repository + routery). Model biznesowy (`net_metering * 0.8`) wymaga rozszerzenia o net-billing, aby aplikacja pozostała użyteczna dla nowych instalacji.

## 🔒 Security Architect

## Model zagrożeń STRIDE — FV Manager v1.12.0

Analiza oparta na dostarczonym kontekście projektu: FastAPI + SQLite + Jinja2, deployment standalone i jako HA Add-on, integracje z Home Assistant API i Tesla Fleet API.

---

### Ocena ogólna: **WYSOKI POZIOM RYZYKA**

Aplikacja zarządzająca danymi finansowymi i energetycznymi, z przechowywanymi tokenami API do systemów domowych, bez warstwy uwierzytelniania i autoryzacji w trybie standalone.

---

| Kategoria STRIDE | Zagrożenie | Poziom ryzyka | Mitygacja |
|---|---|---|---|
| **Spoofing** | Brak uwierzytelniania w trybie standalone — każdy z dostępem sieciowym ma pełną kontrolę nad aplikacją (odczyty, inwestycje, usuwanie danych, dostęp do tokenów HA) | **KRYTYCZNY** | Dodać middleware uwierzytelniania (np. HTTP Basic Auth lub API key) dla trybu standalone. W trybie HA ingress chroni sesja HA — ale standalone na porcie 8010 jest otwarty |
| **Spoofing** | Brak tokenów CSRF w formularzach POST (`/odczyty/{id}/usun`, `/inwestycje/nowa`, `/inwestycje/{id}/usun`, czyszczenie bazy) — atakujący może spreparować stronę z auto-submitem | **WYSOKI** | Wdrożyć CSRF protection — FastAPI nie ma wbudowanego, użyć `starlette-csrf` lub ręczny token w hidden field + walidacja server-side |
| **Spoofing** | Formularz importu CSV — brak weryfikacji źródła uploadu, brak limitu rozmiaru pliku | **ŚREDNI** | Dodać limit rozmiaru pliku (`UploadFile` + check `content_length`), walidacja MIME type |
| **Tampering** | Token HA (`ha_token`) przechowywany w SQLite jako plaintext w tabeli `ev_settings` — każdy z dostępem do pliku `fv.db` odczyta token | **KRYTYCZNY** | Szyfrować token at-rest (np. `cryptography.fernet`) lub przenieść do zmiennych środowiskowych / HA secrets. Token HA daje dostęp do całej instalacji smart home |
| **Tampering** | Endpoint czyszczenia bazy danych ("Niebezpieczna strefa" na `/import`) — brak potwierdzenia server-side, jedyne zabezpieczenie to `confirm()` w JS | **WYSOKI** | Wymagać dodatkowego potwierdzenia server-side (np. wpisanie "USUŃ" w polu tekstowym), dodać auth guard |
| **Tampering** | Import CSV — brak walidacji typów danych po stronie serwera (czy `production_kwh` to float, czy `period` ma format `YYYY.MM`). Złośliwy CSV mógłby wstrzyknąć nieprawidłowe dane | **ŚREDNI** | Dodać ścisłą walidację każdego pola w importerze CSV: typy, zakresy, format okresu. Pydantic model na wejście |
| **Tampering** | Zewnętrzne zasoby CDN (flatpickr, Chart.js) ładowane bez atrybutu `integrity` (SRI) — supply chain attack przez CDN | **ŚREDNI** | Dodać atrybuty `integrity` i `crossorigin` do wszystkich tagów `<script>` i `<link>` z CDN, lub serwować lokalnie |
| **Repudiation** | Brak logowania operacji — usunięcie odczytu, inwestycji, czyszczenie bazy, zmiana tokenów HA nie pozostawia śladu | **ŚREDNI** | Dodać tabelę `audit_log` (timestamp, action, details). Logować co najmniej: DELETE, import, zmiana ustawień HA, czyszczenie bazy |
| **Repudiation** | Brak identyfikacji użytkownika — w kontekście HA Add-on wielu domowników może mieć dostęp, nie wiadomo kto co zmienił | **NISKI** | W trybie HA: przekazywać `X-Ingress-User` do audit logu. W standalone: auth jednoznacznie identyfikuje sesję |

## Kluczowe rekomendacje bezpieczeństwa

1. **[KRYTYCZNY]** Wdrożyć uwierzytelnianie w trybie standalone — HTTP Basic Auth z hasłem z env var jako minimum. Bez tego każdy w sieci lokalnej ma pełną kontrolę nad danymi finansowymi i tokenami smart home.

2. **[KRYTYCZNY]** Zaszyfrować token HA w bazie danych — użyć `cryptography.fernet` z kluczem z env var. Alternatywnie: przenieść tokeny wyłącznie do zmiennych środowiskowych / HA secrets i nie przechowywać w SQLite.

3. **[WYSOKI]** Dodać ochronę CSRF do wszystkich formularzy POST — szczególnie usuwanie danych i czyszczenie bazy. Biblioteka `starlette-csrf` lub ręczny token.

4. **[WYSOKI]** Ograniczyć import CSV — limit rozmiaru pliku (5 MB), walidacja typów i zakresów pól, limit liczby wierszy (np. 1000).

5. **[WYSOKI]** Walidacja `ha_url` przed wykonaniem requestu — zapobiec SSRF. Whitelist schematów, blokada adresów wewnętrznych (metadata endpoints chmur, localhost jeśli nie oczekiwany).

6. **[WYSOKI]** Pinować wersje zależności w `requirements.txt` — obecnie wszystkie bez wersji, podatne na dependency confusion i nieoczekiwane breaking changes.

7. **[ŚREDNI]** Dodać nagłówki bezpieczeństwa HTTP — middleware FastAPI z `X-Content-Type-Options: nosniff`, `X-Frame-Options`, `CSP`, `Referrer-Policy`.

8. **[ŚREDNI]** Dodać atrybuty SRI (`integrity`) do zasobów CDN (flatpickr, Chart.js) — ochrona przed kompromitacją CDN.

9. **[ŚREDNI]** Audit log — tabela logująca operacje destrukcyjne (DELETE, CLEAR, zmiana tokenów) z timestampem.

10. **[NISKI]** Dockerfile — rozważyć multi-stage build, non-root user, read-only filesystem z wyjątkiem `/data`.

## 🔍 Architekt-Krytyk

## Kwestionowane założenia

- **[Skala problemu net-metering]**: Wszyscy czterej architekci oznaczają hardcoded `0.8` jako "krytyczny" lub "wysoki" priorytet — ale **żaden nie zweryfikował, dla kogo ta aplikacja jest**. README mówi wprost: "Model oszczędności oparty na **starym net-meteringu**". `project.json` wskazuje jednego maintainera ("Tomek"), `repository.json` potwierdza. To jest **narzędzie osobiste prosumenta na starym kontrakcie**, nie produkt SaaS. Rekomendacja "wyodrębnij `SettlementStrategy` jako enum" jest architektonicznie poprawna, ale nazywanie tego "krytycznym" dla apki jednego użytkownika to inflacja priorytetów.

- **[Walidacja jako P1 bezpieczeństwa]**: Solution Architect stawia walidację Pydantic jako priorytet #1 (bezpieczeństwo), ale **nikt nie przeczytał `main.py`** — plik nie został dostarczony w kontekście. Twierdzenie o "raw SQL rozrzuconym po `main.py`" i "brak parametryzacji" to **spekulacja, nie audyt**. `aiosqlite` domyślnie używa parametryzowanych zapytań (`?` placeholders). Diagnoza "SQL injection — prawdopodobieństwo średnie" bez zobaczenia ani jednej linii kodu endpointów to fałszywy alarm lub co najwyżej hipoteza do zweryfikowania.

- **[God Object `main.py` >800 linii]**: Solution Architect twierdzi "prawdopodobnie >800 linii" — to **zgadywanie**, nie analiza. Przy 9 endpointach CRUD + 3 integracje + helpery, plik może mieć 400-600 linii, co jest akceptowalne dla FastAPI monolitu. Rekomendacja rozbicia na 7 routerów (dashboard, readings, investments, roi, ev, import_export, integrations) dla aplikacji jednego użytkownika to **overengineering**, który zwiększy liczbę plików bez proporcjonalnej wartości.

- **[Backup jako "priorytetowe"]**: Enterprise Architect oznacza backup jako 🔴 i "priorytetowe", ale **pomija fakt, że backup SQLite to `cp fv.db fv.db.bak`** — jedna komenda. CSV eksport odczytów już istnieje. W HA Add-on `/data/` jest na persistent volume, który HA Supervisor obejmuje swoim systemem snapshotów. Problem jest realny, ale dramatycznie przeszacowany.

- **[Ekstrapolacja liniowa break-even]**: **Żaden architekt nie zakwestionował modelu predykcyjnego**. Produkcja fotowoltaiczna jest **silnie sezonowa** — zimą 50-80 kWh, latem 500+ kWh. Średnia miesięczna z 12 miesięcy daje sensowne przybliżenie, ale z 3-4 miesięcy (np. same letnie) — absurdalnie optymistyczną prognozę. Nikt nie sprawdził, czy `months_to_roi` jest wiarygodny przy krótkim horyzoncie danych.

## Pominięte ryzyka i scenariusze

- **Sezonowość w kalkulacjach**: `avg_monthly_savings` w `calc_roi` to prosta średnia arytmetyczna. Jeśli użytkownik zaczął zbierać dane od maja (500+ kWh produkcji), to prognoza ROI będzie drastycznie optymistyczna — zima obniży średnią o 60-70%. Nikt nie zaproponował ani ważonej średniej, ani minimum 12 miesięcy danych przed ekstrapolacją.

- **`openpyxl` w `requirements.txt`**: Import z Excela usunięty w v1.5.0, `importer.py` oznaczony jako "legacy, nieużywany" przez BA — ale **`openpyxl` nadal jest w zależnościach**. Nikt nie złapał martwej zależności. To nie jest krytyczne, ale Security Architect martwi się o "dependency confusion" przy braku pinów wersji, a jednocześnie nie zauważa, że jedna z zależności jest w ogóle niepotrzebna.

- **Wszystkie wersje z datą 2026-04-19**: CHANGELOG pokazuje, że wersje od 1.0.0 do 1.10.0 (10 wydań!) mają **identyczną datę**. To oznacza rapid-fire development w jednym dniu — prawdopodobnie sesję z AI. Żaden architekt nie zasygnalizował ryzyka związanego z jakością kodu wyprodukowanego w takim tempie: brak code review, brak testów regresyjnych między wersjami, prawdopodobne skróty.

- **Formuła `savings_kwh` — poprawność biznesowa**: `savings_kwh = auto_consumption + min(net_metering_pool, taken_from_grid)`. Nikt nie zweryfikował, czy to jest poprawny model net-meteringu. W rzeczywistości pula 80% jest rozliczana w cyklach 12-miesięcznych, a nie per miesiąc. Jeśli w lipcu oddajesz 300 kWh, to pula 240 kWh jest dostępna **w przyszłych miesiącach**, nie tylko w bieżącym. Obecna formuła traktuje każdy miesiąc niezależnie, co **zaniża oszczędności w miesiącach nadprodukcji i zawyża w miesiącach podkonsumpcji**.

- **`period TEXT NOT NULL UNIQUE`**: Format okresu to prawdopodobnie "YYYY.MM" (z importera), ale **nie ma CHECK constraint** na format. Co się stanie, gdy użytkownik wpisze "2024-01" zamiast "2024.01"? Albo "styczeń 2024"? Formularz HTML nie jest dostarczony w pełni — nie wiemy, czy wymusza format.

- **Testy pokrywają happy path**: 5 testów w `test_calculations.py` — brak testów dla: ujemnych wartości, `production=0`, `sent_to_grid > production` (fizycznie niemożliwe, ale co robi formuła?), `price_per_kwh=0`, ekstremalnie dużych wartości. `auto_consumption = production - sent_to_grid` — jeśli `sent > production`, dostajemy ujemną autokonsumpcję. Importer to odrzuca, formularz — prawdopodobnie nie.

## Sprzeczności w zespole

- **Business Analyst vs Security Architect**: BA explicite wyklucza autentykację ("Won't Have: Autentykacja / multi-user — aplikacja jednoosobowa") i akceptuje standalone bez auth. Security Architect oznacza brak auth jako **KRYTYCZNY**. Kto ma rację? Jeśli to narzędzie osobiste na domowym LAN za routerem, auth jest nice-to-have. Jeśli ktokolwiek planuje wystawić to na zewnątrz — critical. **Brakuje decyzji o modelu zagrożeń** (threat model): domowa sieć z NAT to nie to samo co VPS w chmurze.

- **Enterprise Architect vs Solution Architect — priorytet refaktoru**: EA mówi "refaktor warstw — priorytet średni, nie blokuje użytkownika". SA mówi "P2/P3 — wydzielenie repository + rozbicie na routery" jako kolejne kroki po walidacji. ## Kluczowe decyzje

- **Formuła net-meteringu: per-miesiąc vs kumulacja roczna** — rekomendacja: przebudować `calc_monthly` / `calc_roi` w `calculations.py` na model kumulacyjny. Obecne `savings_kwh = auto_consumption + min(net_metering_pool, taken_from_grid)` zaniża oszczędności latem (nadwyżka puli przepada) i zawyża zimą. Roczna suma może wychodzić zbliżona, ale break-even projection z krótkim horyzontem danych jest niewiarygodny.

- **Walidacja danych wejściowych: gdzie i ile** — rekomendacja: minimum `sent_to_grid <= production` w formularzu ręcznym i imporcie CSV. Importer Excela to sprawdza (linia `if sent > prod: reject`), formularz — prawdopodobnie nie. Ujemna autokonsumpcja psuje cały łańcuch kalkulacji.

- **Token HA: SQLite vs env var** — rekomendacja: przenieść `ha_token` wyłącznie do zmiennej środowiskowej. Token w plaintext w `fv.db` to ryzyko fizycznego bezpieczeństwa (zamki, alarmy, kamery). Koszt zmiany minimalny, konsekwencja wycieku — poważna.

- **Refaktor architektury (routery, repository, Pydantic)** — rekomendacja: **odroczyć** do momentu decyzji o dalszym rozwoju. Dla stabilnej aplikacji jednego użytkownika — niepotrzebny koszt.

## Ryzyka do adresowania

- **Błędna formuła oszczędności** — mitygacja: przebudowa na model kumulacji puli w cyklu rocznym. Wymaga stanu puli (`carry_over_pool`) przenoszonego między miesiącami. To jedyna zmiana wpływająca na core value proposition.

- **Sezonowość w prognozie break-even** — mitygacja: dodać ostrzeżenie gdy `months_measured < 12` ("Prognoza oparta na N miesiącach — pełny cykl roczny zwiększy wiarygodność"). Prosument zaczynający od maja dostanie absurdalnie optymistyczną prognozę.

- **CSRF na destrukcyjnych formularzach** — mitygacja: token CSRF na `POST /import/clear`, `/odczyty/{id}/usun`, `/inwestycje/{id}/usun`. Atakujący nie musi być w sieci — wystarczy złośliwa strona otwarta w przeglądarce, która wyśle `POST` na `localhost:8010`.

- **Martwa zależność `openpyxl`** — mitygacja: usunąć z `requirements.txt`, rozważyć usunięcie `importer.py`. Zero kosztu, zmniejszony attack surface.

## Pytania do Product Ownera

1. **Czy aplikacja jest "gotowa", czy planowane są kolejne funkcje?**
   → Decyzja zależna: refaktor na routery/repository/Pydantic ma sens tylko przy aktywnym rozwoju. Jeśli app jest stabilna — jedyne priorytety to poprawka formuły i walidacja wejścia.

2. **Jaki jest Twój faktyczny model rozliczeń z operatorem — stary net-metering z cyklem rocznym czy inna formuła?**
   → Decyzja zależna: implementacja kumulacji puli 80% w cyklu 12-mies. vs ewentualnie inny model (net-billing, indywidualny kontrakt).

3. **Ile miesięcy danych masz aktualnie w bazie?**
   → Decyzja zależna: czy prognoza break-even jest dziś wiarygodna, czy potrzebuje guardrail (<12 mies. ostrzeżenie).

4. **Czy aplikacja jest wystawiona wyłącznie na domowym LAN, czy kiedykolwiek dostępna z zewnątrz?**
   → Decyzja zależna: priorytet auth (ŚREDNI dla LAN, KRYTYCZNY dla publicznego dostępu).

## Następne kroki

1. **Zweryfikować `main.py`** — żaden architekt nie miał dostępu do tego pliku, a większość spekulacji (SQL injection, rozmiar, jakość kodu) dotyczy właśnie jego. Przed jakąkolwiek implementacją — przeczytać i potwierdzić/obalić hipotezy zespołu.
2. **Poprawić formułę net-meteringu** — przebudować `calc_monthly`/`calc_roi` na model kumulacyjny z pulą przenoszoną między miesiącami. Zaktualizować testy w `test_calculations.py` o scenariusze sezonowe (lato→zima carry-over).
3. **Dodać walidację `sent_to_grid <= production`** w formularzu odczytu i imporcie CSV.
4. **Przenieść `ha_token` z SQLite do env var** — usunąć kolumnę z tabeli `ev_settings`, odczytywać wyłącznie z `os.environ`.
5. **Usunąć `openpyxl`** z `requirements.txt` i rozważyć usunięcie `importer.py`.
6. **Dodać ostrzeżenie** na dashboardzie / ROI gdy `months_measured < 12`.
